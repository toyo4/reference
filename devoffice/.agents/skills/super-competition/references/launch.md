# 参加者の起動手段と注意点

本文の条件を実現するための具体的な手段と落とし穴。必要な操作の節を参照する。以下は2026-10-26までに確認した公式仕様に基づく。実行時のツール定義・CLIヘルプ・公式資料で、利用できるモデルと設定方法を確かめる。

## コンペ開始前のClaude CLI確認

参加者へお題を送る前に、参加者を起動するのと同じ実行ファイル・認証方式・実行環境で確認する。

1. `claude --version`と必要に応じて`claude doctor`で、版と導入方法を確認する。未導入ならCLIの準備が必要なことを共有する。
2. 公式の最新リリースと比較し、古ければ導入方法に合う手段で更新する。ネイティブ版の`claude update`は設定済みチャネルに従うため、`stable`で更新済みでも最新リリースと同じとは限らない。最新へ移す必要があれば公式の`claude install latest`など、導入方式に合う更新を行う。Homebrew等はそのパッケージ・チャネルの更新手段に従う。更新後に実際に起動する版を再確認し、配信遅延や管理制約で最新にできない場合は理由を共有する。
3. `claude auth status`の状態と終了コードを確認する。未認証・期限切れなら、Toyoshiに`claude auth login`による認証を案内し、本人の認証完了後に再確認する。
4. 使用する最新Fable・OpusとHigh・Mediumの対応を確認する。モデル別名の解決先はプロバイダーや設定で変わるため、`fable`・`opus`という指定だけで最新版と断定しない。
5. ログイン状態の表示だけでは認証の有効性や対象モデルの利用可否を確かめきれない場合は、同じ設定でFable・Opusの短い応答を得て確認する。これは本題の候補作成前の疎通確認とし、ファイル操作をさせない。認証エラーなら再認証へ戻り、通信障害・利用上限・モデル利用権の問題は認証切れと区別する。

## Astra・Sol・Luna

起動ツールのモデル名と推論設定の対応を、実行時のツール定義で確認する。独立文脈と個別の設定を両立できる起動方法を選ぶ。たとえば`fork_turns="none"`を使える環境では、コンペごとに新規起動し、共通資料を明示して渡す。前の参加者への追加指示は、同じコンペ内の修正・再検証に使えるが、次のコンペの新規文脈にはならない。

起動直後の`pwd`・HEAD・対象ソースの差分またはハッシュを、本文が求める実行条件の確認に使える。主催者はツールの起動IDと参加者の記録を対応づけ、完了を追跡して成果の所在を回収する。

## Fable・Opus

Claudeを実際に呼び出す際、実行環境の承認申請が必要な場合は、既存の本人許可と、今回の対象資料・送信先（Anthropic）・操作の範囲を具体的に記す。疎通確認の成功だけでは、本題の実行が許可・審査を通ることを確認できない。

Fable用と独立Opus用の各ワークツリーをcwdにし、現在のセッションの実行ツールから別々の`claude -p`プロセスを起動する。`--model`に確認済みの最新モデルを指定し、Fableは`--effort high`、独立Opusは`--effort medium`を明示する。共通のお題は標準入力やファイルから渡し、長い依頼文をシェルコードへ直接埋め込まない。

`--output-format json`などで結果を回収する。通常は`--no-session-persistence`で保存済みのCLI会話を増やさず、成果と必要な実行記録を別途保存する。この指定ではCLI会話を再開できない。新しいコンペでは新規会話として起動し、前回の参加会話の`--continue`・`--resume`も使わない。同じコンペの継続を新しいプロセスで行う場合は、そのコンペの共通条件・候補・判断記録を渡して続けられる。割当済みワークツリーを重ねて作る`--worktree`は使わない。

パスを限定する許可ルールでは、組込みファイル編集ツールの書込みを`Edit(path)`で制御し、`Write(path)`は一致しない。絶対パスは`//`で始める（例: `Edit(//Users/example/worktree/candidate/**)`）。実際の担当範囲に置き換え、実行時の[公式権限仕様](https://code.claude.com/docs/en/permissions)で確認する。このルールだけで、Bash経由のPythonなどが内部で行うファイル操作まで制限されるわけではない。ファイルツールの許可範囲と、実行環境によるファイルシステムの隔離を区別する。

Bashの許可ルールと実コマンドの形が合わないと、非対話実行では検証が拒否されたまま候補が終わることがある。`git -C <path>`、インタプリタの絶対パス、複合コマンドなど、実際に使う形に合わせて限定ルールを渡す。複数のルールはCLIヘルプに従って個別の引数にすると、空白や区切りの解釈を確認しやすい。参加者が許可設定を推測せずに作業できるよう、実在するランタイムの所在と版、許可したコマンドの形と作業範囲を、参加者と補助役にも共通資料で伝える。必要なら同じ設定で代表的な操作を短く試すと手戻りを減らせる。CLI内のルール不一致なら許可済みの担当範囲で実行形かルールを直し、実行環境の審査拒否とは区別する。

許可した単独コマンドに`cd … &&`や`; echo $?`を足すと、限定ルールに一致しなくなることがある。単独形を許可した環境では、その形で個別に実行する方法も共通資料に添えられる。

プロセスのハンドル／起動ID、CLI内部の実行ID、cwd、実際のモデル・推論設定、成果の保存先を対応づける。設定の自己申告だけに頼らず、起動メタデータやCLIの実行記録でも確認する。終了コード・エラー・成果ファイルを確認する。

### Fable配下のOpus

FableのCLI実行に`--agents`で、その実行だけのOpus作業係を定義する。`model`は確認済みの最新Opus、`effort`は`medium`とする。

親のHighを`CLAUDE_CODE_EFFORT_LEVEL`で強制すると子のMedium指定も上書きされる。この変数やモデルを強制する設定が競合していないか確認し、必要な調整は当該CLIプロセスに限定する。親子それぞれの起動メタデータとCLI実行記録で、適用されたモデル、補助役の実行と返却を確かめる。実効effortが記録に現れない場合は、起動引数・`--agents`の定義と上書きする設定の有無を根拠とし、実効値を直接観測したとは記さない。指定構成そのものが不明な場合は、確認できた扱いにしない。
