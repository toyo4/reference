# ペルソナによるフィードバック

GPT-6.1 Terra（Light）をサブエージェントとして起動し、利用者として何を理解し、どう動き、どこで迷い、使いたいと感じるかを得る。E2Eの完走や仕様への適合確認に限定しない。

Lightを使うのは、人は普段、ツールを使うたびに深く考え込むわけではないため。推理を重ねてプロダクトの説明不足を補わせず、目に入る情報からの自然な反応を得る。わざと間違わせたり、不注意な人物を演じさせたりする意図ではない。

## 準備と起動

依頼と対象プロダクトのpremises・利用者像から、試す対象、利用者の目的、ペルソナを定める。指定がなければ、今回の問いに合う一人を選び、仮定を明記する。人物設定は目的に関係する経験・知識・利用状況に絞る。

親エージェントが入口、利用可能な道具、必要なテスト環境を整える。ペルソナには利用者が持ち得る背景・目的・入口・テストデータと、適用されるAGENTS.md・操作の許可範囲を渡す。実装内部、正解の操作手順、既知の問題、開発側の意図、期待する評価を先に教えない。

`collaboration.spawn_agent`を次の実引数で呼ぶ。`message`には、具体的なペルソナ・目的・対象への入口・操作手段・制約と、次節の利用者役への指示を入れる。

```json
{
  "task_name": "persona_feedback",
  "model": "gpt-6.1-terra",
  "reasoning_effort": "low",
  "fork_turns": "none",
  "message": "今回の対象に合わせた利用者役への依頼"
}
```

LightはUI表記で、実引数は`low`。モデル名をプロンプトに書くだけで済ませず、起動時に指定する。`fork_turns: "none"`で開発側の会話を継承しないため、必要な条件は依頼文に含める。指定モデル・設定が使えなければその制約を報告し、黙って別の構成へ置き換えない。複数のペルソナが必要な場合はそれぞれ新規の文脈で起動し、互いの結果を渡さない。利用者役にこのスキルを再起動させない。

## 利用者役への指示

- 与えられたペルソナとして、利用者に見える情報から自然に理解・選択し、目的を達成しようとする。開発者のレビュー、網羅的なバグ探し、内部実装の調査・修正は担当しない。
- 必要なら読み直す、戻る、利用者向けヘルプを探すなど、自然な回復を試してよい。長く推理して正解を探し続けず、通常なら諦めるところでは、その理由と未達の目的を残す。
- 操作できるものは実際に試す。文章・画像・非動作の試作品は、見えた内容への理解や印象を返す。未操作の挙動は予想と明示し、アクセスできない対象を見たことにしない。道具・認証・起動の問題は、プロダクトへの反応と区別して親へ返す。
- 適用される作業指示と操作の許可範囲を守る。ブラウザを使う場合はChrome。許可されていない外部送信・課金・実データの削除などが必要なら、その手前までの観察を返す。
- 重要な場面の「見たもの → 理解・期待 → 行動 → 実際の結果」を短く残す。伝わったこと、助かったこと、迷い・誤解・離脱を、該当する文言・画面・操作順や取得できたスクリーンショットと結び付ける。
- 最後に、試した範囲、目的の達成・未達と理由、全体の印象を返す。使い続けたいかなど、今回の目的に関係する感想も添える。主観や改善アイデアは実際の操作・表示と区別する。

## 観察と報告

親は観察中に正解を教えたり、同じ画面を並行操作したりしない。環境の準備を助けた場合は、支援前後の試行を分ける。終了後、次を簡潔に整理してユーザーへ返す。

- **条件と範囲**：使用モデル・effort、ペルソナの仮定、対象・入口、実際に確認した範囲と未確認事項。
- **体験と根拠**：目的の達成状況、伝わった点、迷いや離脱を生んだ場面。観察した操作・表示と、ペルソナの理解・感想を分ける。
- **示唆**：親による解釈・改善案を、観察から導いた提案と明示し、目的への影響が大きいものから示す。

開発側の理解でペルソナの誤解を取り消さない。原因の技術的な確認や実装修正は、依頼の範囲に従って別の作業として扱う。これはAIによる模擬体験であり、実利用者の反応や発生頻度を実証した結果として扱わない。

設計の見直しや検証済み範囲の確認には、[設計理由と検証記録](references/design-rationale.md)を参照する。
